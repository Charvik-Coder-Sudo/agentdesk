## 4. Failures (defects found)

All three are Low severity: they do not break a Phase 1 acceptance criterion in normal use, but they violate the robustness expectation behind NFR-012 (every startup error names what to do) or FR-010 (3) (retention).

### D-1. Twelve backups within one second crash: the newest backup is deleted at once and `create_backup` raises FileNotFoundError

- Requirement: FR-010 (3), FR-009, FR-011.
- Test: `tests/test_tst_backups.py::test_tst_twelve_backups_in_one_second_keep_the_newest_ten` (clock frozen to one second).
- Steps: with a started installation, call `create_backup(settings, "manual")` 12 times within the same second (a script loop, or repeated clicks and calls).
- Expected: every call returns a backup that exists; after the 12th, 10 files remain and the newest is among them.
- Actual: the 12th call raises `FileNotFoundError: ... agentdesk-20261031-120000-manual.db` from `parse_backup_name` at `app\database\backup.py:146`. Through the API this would be an unhandled error and a 500 "internal_error".
- Evidence: the traceback `app\database\backup.py:146: in create_backup -> parse_backup_name -> path.stat() FileNotFoundError`. It also happened once organically in an earlier version of my test that ran 12 real backups quickly across a second boundary.
- Cause: `_unique_path` picks the lowest free name. After 11 backups in the same second, retention deletes the base name (sequence 1, the "oldest"). The 12th backup then gets the base name again, is sorted as the oldest, and `prune_backups` removes it immediately.
- Likely location: `app\database\backup.py` `_unique_path` (reuse of a freed base name), `list_backups` sort key, `prune_backups` (should never remove the file just created).
- Suggested fix for the developer: number new files after the highest existing sequence for that second (or add a sub-second or counter part to the name), and have `create_backup` exclude or protect the newly created file when pruning.

### D-2. A data folder that is a file (or lies below a file) ends in a raw FileExistsError instead of a plain message

- Requirement: NFR-012 (startup errors name the fix), NFR-011.
- Tests: `tests/test_tst_config_cli.py::test_tst_data_dir_that_is_a_file_gives_startup_error_not_a_traceback` and `::test_tst_data_dir_below_a_file_gives_startup_error_not_a_traceback`.
- Steps: `Settings(data_dir=<an existing file>)` or `<an existing file>\data`, then `create_app(settings)` (the same call `python -m app` makes after loading `AGENTDESK_DATA_DIR`).
- Expected: `StartupError` with a sentence saying the data folder is not a folder and what to do (which `python -m app` prints without a traceback).
- Actual: `FileExistsError: [WinError 183] Cannot create a file when that file already exists` from `app\main.py:122 (folder.mkdir(parents=True, exist_ok=True))`. `app\__main__.py` only catches `StartupError`, so the owner would see a traceback (by code reading; I did not run the CLI for this case).
- Likely location: `app\main.py` `run_startup`, around the three `mkdir` calls (catch `OSError` and raise `StartupError`).

### D-3. An empty migrations folder ends in a raw `sqlite3.OperationalError: no such table: app_settings`

- Requirement: FR-012, NFR-012.
- Test: `tests/test_tst_database.py::test_tst_empty_migrations_folder_gives_a_clean_startup_error`.
- Steps: `create_app(settings, migrations_dir=<empty folder>)` on a new data folder. (In real use this happens if the `migrations` folder is emptied or its files are renamed wrongly, because wrongly named files are ignored.)
- Expected: `StartupError` saying no migration files were found and to restore the folder from Git.
- Actual: `sqlite3.OperationalError: no such table: app_settings` from `_ensure_instance_settings` (`app\main.py:113`, called at line 152); an `agentdesk.db` containing only `schema_migrations` is left behind. The next start with correct migrations works, so there is no data loss.
- Likely location: `app\main.py` `run_startup` / `app\database\migrations.py` `discover_migrations` (raise `MigrationError` when no file is found, or catch `sqlite3.Error` around the instance-settings step).

## 5. Observations (no failing test; for the developer and owner to judge)

- O-1. The read-only startup check of a damaged WAL-mode database creates empty `agentdesk.db-wal` and `-shm` files next to it. The database file stays byte-identical (SHA-256 checked, FR-013 (3) met). The restore script handles leftover sidecars correctly (tested). Cosmetic.
- O-2. `HEAD /api/v1/health` answers 405 (only GET is routed). Harmless unless a monitoring tool uses HEAD.
- O-3. `start.bat` plus Ctrl+C: the server stops gracefully and the port is freed (M4), but cmd asks "Terminate batch job (Y/N)?" because the script runs the server without `call`/`exit` handling. That is standard cmd behaviour; the owner types Y. Worth a sentence in the README.
- O-4. `formatBytes(NaN)` returns "NaN bytes" and `formatBytes(Infinity)` returns "Infinity GB". Unreachable with the real API values.
- O-5. `router.js` calls `decodeURIComponent` on route parameters without a try/catch, so a malformed `%` escape in a parameter would raise a URIError. No Phase 1 route has a parameter (test records this, does not assert on it).
- O-6. SQLite reads a database whose very last page is cut by one byte (zero-filled) and `quick_check` says ok; cutting a whole page or more is detected and refused (tested). This is SQLite behaviour, not an AgentDesk fault.
- O-7. A migration file that contains its own `BEGIN`/`COMMIT` is forbidden only by a comment in the runner; there is no enforcement. Proposed test below.
- O-8. `test_tst_javascript_syntax_check...` and `test_tst_node_unit_tests...` use `skipif` when Node is missing (DEC-022: a skipped check is never evidence). In this run Node v24.18.0 was present and both ran (0 skipped).
